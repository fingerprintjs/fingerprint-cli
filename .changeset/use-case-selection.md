`fingerprint integrate` in a repo that already has Fingerprint audits the code first, reports which Get Started steps are done (installed, server-side verification, custom subdomain) and asks "What's next?" with only the remaining steps; the remaining-steps option is offered as soon as server-side verification is done, so skipping the custom subdomain does not block it. When the skills repo provides use-case skills, it asks before the first step how Fingerprint should be set up: the basic installation (the default) or one or more use cases (account takeover, coupon abuse, ...). In a repo with a backend, install and server-side verification then land in one run. A frontend-only repo is reminded that the backend completes the setup; when it points at its backend from the menu, that step can also read and edit the frontend, so the form it wired sends the event ID to the route the step protects. The chosen use cases go to the agent for every step. In a backend-only repo the first "What's next?" entry is to bring in the frontend, since the backend's check needs an event ID the frontend sends: it asks for the frontend repo's path and installs Fingerprint there. `--yes` and `--ci` run the basic integration.
