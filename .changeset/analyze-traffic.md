New `fingerprint analyze`: reads the workspace's recent identification events with the Server API key from the login bundle and says which pages need protecting. Bad bots and high Suspect Scores are counted over the whole window with the Server API's own filters, so the numbers hold on a busy workspace; shares, replayed ids, confidence and SDK versions come from a sample spread evenly across the window (`--max` events, ten time slices) rather than the newest events, which on a busy site cover hours, not days. The report lists only pages with signals and suggests what to do: a Rules Engine rule where bad bots cluster, single-use event ids where replays show up, a custom subdomain where confidence is low, and server-side verification when the repo never reads events back. Then it asks which suggestion to apply: the integrate agent does that one step in the backend (asking where the backend lives when the repo has none), and the menu comes back until you stop. `--days`, `--max`, `--path` and `--json`; `--ci` prints the report only. Only aggregates are printed, never an event or visitor id. Staging (`FINGERPRINT_ENV=staging`) resolves the staging Server API; `FINGERPRINT_SERVER_API_URL` overrides it.
